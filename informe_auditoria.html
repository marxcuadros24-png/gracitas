Resumen Ejecutivo y Dictamen de Auditoría

El presente informe documenta los resultados de la auditoría de seguridad informática en modalidad Caja Blanca (White-Box Code Audit) efectuada sobre la plataforma GraCitas, solución web desarrollada para la gestión deportiva y reserva de canchas sintéticas en el distrito de Coracora (Parinacochas, Ayacucho).

Controles Sólidos
Dictamen del Auditor
La aplicación evidencia buenas prácticas perimetrales en prevención de ataques de fuerza bruta (Rate Limiting dinámico por IP y credencial), invalidación de sesiones y tokens JWT con lista negra criptográfica. Sin embargo, se identificaron vulnerabilidades críticas en la lógica de negocio y en el control de acceso multi-inquilino (IDOR) que comprometen la privacidad de los deportistas y la integridad contable de los complejos deportivos.

Fichas Técnicas de Hallazgos y Remediaciones

ID: gracitas:idor:reserva-comprobante-authz
1. Fuga de Comprobantes y Datos Personales entre Propietarios (IDOR)
Severidad Alta
El controlador de comprobantes (/reserva/comprobante/{codigo}) solo comprueba la propiedad si el usuario autenticado tiene rol cliente. Si un usuario se registra con rol propietario, la condición $user->isCliente() es falsa y el sistema permite descargar o visualizar los comprobantes de cualquier complejo deportivo de la competencia.
Archivo Afectado: app/Http/Controllers/ReservaClienteController.php (Líneas 126–131)
Datos Expuestos: Nombres completos de deportistas, números telefónicos, correos electrónicos, importes pagados y método de cobro (Efectivo/Yape/Plin).
Código Vulnerable:
// app/Http/Controllers/ReservaClienteController.php:127 $user = Auth::user(); if ($user->isCliente() && $reserva->cliente_id !== $user->id) { abort(403, 'No tienes permiso para ver esta reserva.'); } // ¡Omite verificar si el usuario propietario es dueño de la cancha reservada!
Solución Técnica (Parche Inmediato):
$user = Auth::user(); if ($user->isCliente() && $reserva->cliente_id !== $user->id) { abort(403, 'No tienes permiso para ver esta reserva.'); } if ($user->isPropietario() && (int)$reserva->cancha->establecimiento->propietario_id !== (int)$user->id) { abort(403, 'No tienes permiso para ver comprobantes de otros establecimientos deportivos.'); }
ID: gracitas:disclosure:public-availability-booking-codes
2. Exposición Pública de Códigos Confidenciales en API de Disponibilidad
Severidad Media
El servicio que calcula los turnos libres concatena el código confidencial de reserva (ej. GC-2611-ABCDE) en la descripción devuelta por la API pública /cancha/{id}/disponibilidad. Cualquier visitante no autenticado puede recolectar sistemáticamente los códigos de reserva de los partidos.
Archivo Afectado: app/Services/AvailabilityService.php (Línea 84)
Código Vulnerable:
// app/Services/AvailabilityService.php:84 } elseif ($reservaSolapada) { $disponible = false; $estado = 'reservado'; $detalle = 'Reservado ('.$reservaSolapada->codigo.')'; // Expone código confidencial }
Solución Técnica:
} elseif ($reservaSolapada) { $disponible = false; $estado = 'reservado'; $detalle = 'Horario reservado'; // Sanitizado sin filtrar códigos internos }
ID: gracitas:race-condition:reservation-double-booking
3. Condición de Carrera Concurrente (Riesgo de Doble Reserva)
Severidad Media
En ReservaClienteController::store, la disponibilidad se verifica con una consulta SELECT sin bloqueo pesimista. Si dos clientes envían la solicitud en el mismo milisegundo por un horario de alta afluencia (ej. viernes noche), ambas transacciones leen cero conflictos y crean dos reservas confirmadas para la misma cancha.
Archivos Afectados: app/Http/Controllers/ReservaClienteController.php (Líneas 68–95) y AvailabilityService.php
Solución Técnica (Bloqueo Pesimista lockForUpdate):
return DB::transaction(function () use ($validated) { // Bloqueo pesimista para serializar la asignación del turno en la cancha seleccionada $cancha = Cancha::where('id', $validated['cancha_id'])->lockForUpdate()->firstOrFail(); $inicio = Carbon::parse($validated['fecha'].' '.$validated['hora_inicio'], 'America/Lima'); $fin = $inicio->copy()->addMinutes((int) $validated['duracion_min']); $verificacion = $this->availabilityService->checkAvailability($cancha, $inicio, $fin); if (! $verificacion['disponible']) { return back()->with('error', $verificacion['mensaje'])->withInput(); } // Procede a crear la reserva de forma estrictamente serializada });
ID: gracitas:data-lifecycle:account-deletion-purges-payments
4. Borrado de Cuenta Purga Pagos Históricos y Altera Contabilidad
Severidad Media
Al eliminar una cuenta de cliente en /perfil, deleteWithRelations() ejecuta un borrado físico en cascada (Pago::whereIn(...)->delete()). Si el usuario ya jugó partidos en fechas anteriores, los registros de dinero cobrado en ventanilla desaparecen para siempre, descuadrando la contabilidad del propietario.
Archivo Afectado: app/Models/User.php (Líneas 158–164)
Solución Técnica (Anonimización en vez de Borrado Físico):
if ($this->isCliente()) { // Conserva las transacciones de pago históricas y anonimiza la referencia al cliente $this->reservas()->update([ 'cliente_id' => null, 'observaciones' => '[Cuenta de cliente eliminada por solicitud del usuario]', ]); }
04

Puntos Fuertes de Seguridad Detectados

Control Implementado Mecanismo Técnico y Efectividad
Rate Limiting Defensivo Configurado en AppServiceProvider.php con límites estrictos: 5 req/min en login/registro, 3 req/min en recuperación de contraseña y 60 req/min en la API. Bloquea eficazmente ataques de fuerza bruta.
Suspensión Inmediata de Usuarios CheckRole.php y la API validan $user->activo. Si un administrador desactiva una cuenta, las sesiones y tokens se invalidan de forma inmediata.
Tokens JWT Criptográficos Firma HMAC SHA-256 con claims personalizados (rol, activo) y revocación en lista negra (blacklist) al cerrar sesión.
WebSockets Seguros (Laravel Reverb) Canales privados private-establecimiento.{id} suscritos únicamente si $establecimiento->propietario_id === $user->id.
