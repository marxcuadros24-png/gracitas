03

Verificación Técnica Detallada de Parches en Código

1. Verificación de Control de Acceso Multi-Tenant en Comprobantes (IDOR) Subsanado al 100%
Auditoría Inicial (16 Noviembre):
El endpoint /reserva/comprobante/{codigo} permitía que un usuario registrado con rol propietario visualizara los comprobantes de canchas ajenas con nombres, teléfonos y montos de clientes de la competencia.
Inspección al 27 Noviembre:
Implementado con éxito. Se inspeccionó ReservaClienteController.php. La empresa implementó la validación que rechaza con error 403 Forbidden a cualquier propietario que intente consultar comprobantes de locales ajenos.
Código Verificado en Repositorio (Commit db07ea0):
// app/Http/Controllers/ReservaClienteController.php (Líneas 128-135) if ($user->isPropietario()) { $propietarioId = (int) ($reserva->cancha?->establecimiento?->propietario_id ?? 0); if ($propietarioId !== (int) $user->id) { abort(403, 'No tienes permiso para ver comprobantes de otros establecimientos deportivos.'); } }
2. Verificación de Protección de Códigos en la API Pública Subsanado al 100%
Auditoría Inicial (16 Noviembre):
La API /cancha/{id}/disponibilidad exponía los códigos confidenciales de reserva (GC-2611-XXXXX) en el campo detalle ante cualquier petición anónima.
Inspección al 27 Noviembre:
Implementado con éxito. Se comprobó en AvailabilityService.php que la interpolación fue eliminada por completo, respondiendo ahora únicamente "Horario no disponible".
Código Verificado en Repositorio (Commit db07ea0):
// app/Services/AvailabilityService.php (Línea 84) } elseif ($reservaSolapada) { $disponible = false; $estado = 'reservado'; $detalle = 'Horario no disponible'; // Sanitizado completamente }
3. Verificación de Bloqueo Pesimista contra Dobles Reservas Subsanado al 100%
Auditoría Inicial (16 Noviembre):
La creación de reservas no bloqueaba la fila de la cancha en base de datos. Peticiones simultáneas en el mismo instante causaban dobles reservas sobre la misma hora.
Inspección al 27 Noviembre:
Implementado con éxito. Se aplicó lockForUpdate() tanto en ReservaClienteController.php como en las reservas manuales de PropietarioReservaController.php.
Código Verificado en Repositorio (Commit db07ea0):
// app/Http/Controllers/ReservaClienteController.php (Líneas 63-65) return DB::transaction(function () use ($validated) { $cancha = Cancha::where('id', $validated['cancha_id'])->lockForUpdate()->firstOrFail(); // La transacción serializa las reservas concurrentes evitando solapamientos
4. Verificación de Preservación Contable al Eliminar Usuarios Subsanado al 100%
Auditoría Inicial (16 Noviembre):
El borrado de cuenta de un cliente ejecutaba Pago::delete() físico, eliminando comprobantes y alterando los reportes mensuales de ingresos de los dueños.
Inspección al 27 Noviembre:
Implementado con éxito. Se modificó User.php. Si el cliente tiene reservas históricas, se anonimizan sus datos personales y se desactiva la cuenta, preservando los pagos intactos.
Código Verificado en Repositorio (Commit db07ea0):
// app/Models/User.php (Líneas 162-174) if ($this->isCliente()) { if ($this->reservas()->exists()) { $this->update([ 'name' => 'Usuario Eliminado', 'email' => 'eliminado_'.$this->id.'_'.time().'@gracitas.local', 'telefono' => null, 'password' => Hash::make(Str::random(32)), 'activo' => false, ]); return; // Preserva registros de pagos intactos para la contabilidad } }
5. Verificación de Invalidación de Correo al Cambiar Email Subsanado al 100%
Auditoría Inicial (16 Noviembre):
Cambiar la dirección de email en /perfil mantenía la cuenta verificada sin enviar confirmación a la nueva dirección.
Inspección al 27 Noviembre:
Implementado con éxito. AuthController.php ahora detecta el cambio de correo, reinicia email_verified_at = null y reenvía el correo de verificación.
Código Verificado en Repositorio (Commit db07ea0):
